🎯 Synthèse de la cause racine
Le blocage résulte de la convergence de trois facteurs :
Conflit d'identité (Preset Custom vs Backend Built-in) :
Le système manipule n8n sous deux identités concurrentes :
D'un côté comme Preset Custom Agent (id: 'builtin-n8n-workflow', préfixé en custom:builtin-n8n-workflow).
De l'autre comme Backend ACP Built-in direct (backend: 'n8n').
Le clic sur ADMIN initialise et injecte les presets dans le store en mémoire. Tant que ce clic n'a pas eu lieu, le hook ne trouve pas l'agent ou subit un état asynchrone non résolu.
Écrasement de l'état initial par la persistance (config.json) :
Dans useGuidAgentSelection.ts, useState('n8n') est immédiatement écrasé au premier rendu par ConfigStorage.get('guid.lastSelectedAgent') (qui contient l'ancienne sélection mémorisée dans votre profil utilisateur Windows %APPDATA%\E-audit\config.json). De plus, si la liste availableAgents est vide au démarrage (attente SWR/IPC), l'effet de repli (fallback) réinitialise la sélection vers un agent valide (ex. Gemini).
Verrouillage de fichiers sous Windows & Nature du Hot Reload Vite :
Vite HMR ne recharge jamais le Main Process (AcpDetector.ts se compile dans out/main/index.js). Sous Windows, des processus orphelins electron.exe restent fréquemment actifs en arrière-plan, posant un verrou exclusif sur out/main/ et empêchant la réécriture des fichiers JS malgré les messages de compilation Vite.

2. Question 1 — Pourquoi selectedAgent peut ne jamais être 'n8n' ?
Cause probable : une conversion incorrecte entre clé de sélection et type backend
Dans votre description, la sélection initiale est :
const [selectedAgentKey, setSelectedAgentKey] =
  useState<string>('n8n');


Mais votre système comporte aussi des agents presets et custom, notamment :
'custom:builtin-n8n-workflow'


Il faut donc vérifier précisément la transformation entre la clé de sélection et le backend.
Cas A — La clé est n8n, mais le code traite uniquement les clés custom:
Exemple de logique potentiellement problématique :
const selectedAgent = selectedAgentKey.startsWith('custom:')
  ? 'custom'
  : selectedAgentInfo?.presetAgentType;


Si selectedAgentKey = 'n8n' et que selectedAgentInfo est undefined, alors selectedAgent peut être undefined au lieu de 'n8n'.
Cas B — selectedAgentInfo cherche uniquement dans availableAgents
Par exemple :
const selectedAgentInfo = useMemo(
  () => availableAgents?.find(agent => agent.id === selectedAgentKey),
  [availableAgents, selectedAgentKey]
);


Si availableAgents ne contient pas l'agent sous l'identifiant n8n, la recherche échoue.

Or, votre architecture décrit deux représentations possibles :
Élément	Valeur possible
Backend	n8n
ID du preset	builtin-n8n-workflow
Clé custom	custom:builtin-n8n-workflow
Nom affiché	n8n Workflow

Ce ne sont pas des identifiants interchangeables. Il faut définir un mapping unique entre ces valeurs.
Correction recommandée : centraliser la résolution
Voici un exemple de logique plus robuste, à adapter aux types et à la structure exacte de vos objets.
type N8nAgentType = 'n8n' | 'n8n-multi-workflow';

const N8N_AGENT_TYPES: readonly N8nAgentType[] = [
  'n8n',
  'n8n-multi-workflow',
];

const isN8nAgent = (
  value: string | undefined
): value is N8nAgentType => {
  return value !== undefined &&
    N8N_AGENT_TYPES.includes(value as N8nAgentType);
};


Puis, dans la résolution de l'agent, évitez que l'identifiant n8n dépende exclusivement d'une recherche dans une liste asynchrone :
const selectedAgent = useMemo(() => {
  if (isN8nAgent(selectedAgentKey)) {
    return selectedAgentKey;
  }

  if (selectedAgentKey.startsWith('custom:')) {
    return 'custom';
  }

  return selectedAgentInfo?.presetAgentType;
}, [selectedAgentKey, selectedAgentInfo]);


Attention : cet exemple ne constitue pas encore un remplacement exact de votre hook. La logique actuelle de sélection des agents classiques doit être conservée, et il faut vérifier les types de retour réels de presetAgentType.
Pourquoi le useMemo peut poser problème ?
Le useMemo ne rend pas les données synchrones. Il ne fait que recalculer sa valeur lorsque ses dépendances changent.

Par exemple :
const selectedAgentInfo = useMemo(
  () => findAgentByKey(selectedAgentKey),
  [selectedAgentKey, availableAgents]
);


Au premier rendu :
selectedAgentKey = 'n8n'
availableAgents = undefined
selectedAgentInfo = undefined


Après la réponse IPC :
selectedAgentKey = 'n8n'
availableAgents = [ ...agents... ]
selectedAgentInfo = résultat de la recherche


Si la clé n8n ne correspond pas aux identifiants de la liste reçue, l'agent ne sera toujours pas résolu.

Le problème n'est donc pas le useMemo en lui-même, mais sa dépendance à une source de données asynchrone et au mapping des identifiants.

3. Question 2 — Le type AcpBackendAll est-il suffisant ?
Non, pas à lui seul.

L'ajout de 'n8n' et 'n8n-multi-workflow' dans AcpBackendAll permet au compilateur de reconnaître ces chaînes dans les endroits qui utilisent effectivement ce type.

Mais il ne garantit pas :
- que AcpBackend contient lui aussi ces valeurs ;
- que les interfaces Conversation, ConversationCreateParams ou Model les acceptent ;
- que le handler IPC accepte type: 'n8n' ;
- que les switches ou dispatchers backend savent traiter n8n ;
- que le runtime a réellement chargé la nouvelle version du code.
Distinction essentielle
export type AcpBackendAll =
  | 'claude'
  | 'gemini'
  | 'n8n'
  | 'n8n-multi-workflow'
  | 'custom';


Si vous utilisez :
type GuidSendDeps = {
  selectedAgent: AcpBackend | 'custom' | 'n8n' | 'n8n-multi-workflow';
};


Cela autorise cette propriété dans GuidSendDeps. Mais le type de la conversation passée à IPC peut encore refuser :
await ipcBridge.conversation.create.invoke({
  type: 'n8n',
  // ...
});


Si conversation.create attend un type différent, élargir GuidSendDeps ne corrige pas cette incompatibilité.
Recommandation : une source unique de vérité
Si ces backends sont des types de conversation réellement supportés par l'application, utilisez un type métier commun à la conversation et au dispatcher, plutôt que d'élargir localement le type de useGuidSend.

Exemple de modèle conceptuel :
export type ConversationBackend =
  | AcpBackend
  | 'n8n'
  | 'n8n-multi-workflow'
  | 'custom';


Puis :
type GuidSendDeps = {
  selectedAgent: ConversationBackend;
};


Et dans les paramètres de création :
type ConversationCreateParams = {
  type: ConversationBackend;
  name: string;
  model: Model;
};


Important : ne créez pas cette nouvelle union si le projet possède déjà un type central équivalent. Il faut d'abord réutiliser et élargir le type existant à la bonne couche.
TypeScript ne valide pas les valeurs à l'exécution
Ce code :
type Backend = 'claude' | 'n8n';

const backend: Backend = 'n8n';


ne crée aucun mécanisme runtime qui active n8n.

Il faut également que le Main Process, les handlers IPC, le factory/dispatcher et le gestionnaire n8n acceptent ce backend.

4. Question 3 — La condition de branche n8n est-elle correcte ?
Votre condition actuelle est valide en TypeScript et en JavaScript :
if (
  selectedAgent === 'n8n' ||
  (isPreset && finalEffectiveAgentType === 'n8n')
) {
  // Création conversation n8n
}


Mais elle est fragile fonctionnellement, car elle dépend de selectedAgent correctement dérivé et de finalEffectiveAgentType correctement calculé.

Si la résolution de l'assistant est précisément le maillon défaillant, cette condition peut ne jamais s'exécuter.
Correction de sécurisation recommandée
Lorsque la clé de sélection est un backend n8n explicite, utilisez-la également dans le dispatch.
const isN8nSelected =
  selectedAgent === 'n8n' ||
  selectedAgentKey === 'n8n' ||
  (isPreset && finalEffectiveAgentType === 'n8n');

if (isN8nSelected) {
  // Création conversation n8n
}


Et pour le multi-workflow :
const isN8nMultiSelected =
  selectedAgent === 'n8n-multi-workflow' ||
  selectedAgentKey === 'n8n-multi-workflow' ||
  (isPreset &&
    finalEffectiveAgentType === 'n8n-multi-workflow');

if (isN8nMultiSelected) {
  // Création conversation n8n multi-workflow
}


Version plus propre avec type guard
type N8nBackend =
  | 'n8n'
  | 'n8n-multi-workflow';

const isN8nBackend = (
  value: string | undefined
): value is N8nBackend => {
  return value === 'n8n' ||
    value === 'n8n-multi-workflow';
};


Utilisation :
const n8nBackend =
  isN8nBackend(selectedAgentKey)
    ? selectedAgentKey
    : isN8nBackend(finalEffectiveAgentType)
      ? finalEffectiveAgentType
      : isN8nBackend(selectedAgent)
        ? selectedAgent
        : undefined;

if (n8nBackend === 'n8n') {
  // Branche workflow simple
} else if (n8nBackend === 'n8n-multi-workflow') {
  // Branche multi-workflow
}


Cette version a un avantage : elle identifie explicitement le backend réel au lieu de répéter plusieurs conditions dispersées.
Mon conseil
Pour votre débogage immédiat, utilisez d'abord la version de sécurisation, puis ajoutez temporairement des logs :
console.log('[GUID SEND DEBUG]', {
  selectedAgentKey,
  selectedAgent,
  selectedAgentInfo,
  isPreset,
  finalEffectiveAgentType,
  n8nBackend,
});


Vous devez obtenir un résultat de ce type avant d'appuyer sur Envoyer :
{
  "selectedAgentKey": "n8n",
  "selectedAgent": "n8n",
  "isPreset": false,
  "finalEffectiveAgentType": "n8n",
  "n8nBackend": "n8n"
}


Le statut isPreset peut varier selon votre implémentation. Le résultat important est que le backend résolu soit bien n8n.

5. Question 4 — Le placeholderModel est-il valide ?
Votre structure :
const placeholderModel = currentModel || {
  id: 'n8n-placeholder',
  name: 'n8n',
  useModel: 'n8n-workflow',
  platform: 'n8n' as const,
  baseUrl: '',
  apiKey: '',
};


Elle est syntaxiquement valide, mais sa validité au regard des interfaces de votre projet ne peut pas être confirmée sans le type exact Model et la signature IPC conversation.create.invoke().
Points à vérifier
Champ	Diagnostic
id	OK si Model exige un identifiant
name	OK si nom affiché obligatoire
useModel	Vérifier si cette propriété est obligatoire et son union
platform	'n8n' as const conserve le type littéral
baseUrl	Peut être vide si le backend n'en dépend pas
apiKey	Peut être vide si la configuration n'utilise pas ce champ
Autres propriétés	Peut manquer des champs requis par l'interface Model

Recommandation de typage
Si votre projet possède une interface Model exportée, préférez un typage explicite :
const n8nPlaceholderModel: Model = {
  id: 'n8n-placeholder',
  name: 'n8n',
  useModel: 'n8n-workflow',
  platform: 'n8n',
  baseUrl: '',
  apiKey: '',
};


Si le modèle est destiné à satisfaire une interface sans effectuer une conversion, satisfies peut être préférable :
const n8nPlaceholderModel = {
  id: 'n8n-placeholder',
  name: 'n8n',
  useModel: 'n8n-workflow',
  platform: 'n8n',
  baseUrl: '',
  apiKey: '',
} satisfies Model;


Ne forcez pas le type par cast pour masquer une incompatibilité réelle.

Par exemple, évitez :
const placeholderModel = {
  // ...
} as Model;


Cette méthode peut supprimer l'erreur du compilateur tout en laissant un objet invalide à l'exécution.
Architecture plus propre
Si n8n ne consomme pas réellement un modèle LLM conventionnel, l'idéal serait que le backend conversationnel n8n ne soit pas dépendant artificiellement d'un Model obligatoire.

Par exemple :
type N8nConversationConfig = {
  type: 'n8n';
  name: string;
  extra: {
    endpoint: string;
    workflowId?: string;
  };
};


Puis l'API de création de conversation pourrait distinguer :
- conversation LLM classique ;
- conversation ACP ;
- conversation n8n.
Cela supprimerait la nécessité de maintenir un faux modèle uniquement pour satisfaire le type.

6. Question 5 — Electron Main Process : pourquoi le rebuild ne s'applique-t-il pas ?
Votre document d'architecture indique que le Renderer et le Main Process ne sont pas compilés ni rechargés de la même façon.
Deux pipelines de développement distincts
Renderer — React

src/renderer/ → Vite → serveur dev → Chromium

HMR généralement disponible

Main Process — Electron / Node

src/main/ → build Electron Vite → out/main/ → processus Electron

Redémarrage du processus nécessaire

Preload

src/preload/ → build → chargement dans le BrowserWindow

Vérifier que la fenêtre charge le preload fraîchement compilé


Pourquoi le build peut réussir sans que le changement soit visible ?
Un build réussi signifie que le processus de compilation a produit des sorties sans erreur bloquante. Cela ne garantit pas que l'application ouverte utilise ces sorties.

Les causes les plus probables sont :
1. Mauvais processus Electron : une ancienne instance reste ouverte.
2. Mauvais dossier de sortie : vous inspectez out/main, mais Electron utilise une autre entrée.
3. Mauvaise configuration de lancement : npm run start démarre un autre script, une autre copie du projet ou une version installée.
4. Renderer en mode dev, Main obsolète : le serveur Vite fonctionne, mais le Main Process ne redémarre pas correctement.
5. State persisté : guid.lastSelectedAgent ou les presets enregistrés écrasent votre valeur par défaut.
6. Migration/configuration : une migration de config ou une valeur déjà sauvegardée restaure un ancien agent.
7. Rebuild partiel : certaines sorties sont mises à jour, d'autres non.
Le cache Electron n'est pas la première cause à rechercher
Un cache Chromium comme GPUCache, Cache, Code Cache ou Service Worker peut affecter le Renderer dans certains cas.

Cependant, un cache Chromium ne réécrit pas normalement votre logique JavaScript du Main Process. Si AcpDetector.initialize() ne contient pas le nouveau code dans le processus exécuté, le problème est davantage lié au build, à l'entrée de démarrage ou au processus actif.

Il faut donc vérifier les fichiers réellement exécutés avant de vider massivement AppData.

8. Symptôme 3 — Pourquoi faut-il cliquer sur ADMIN ?
Ce symptôme est particulièrement important, car il ne correspond pas forcément à un problème de cache.

Si la liste des assistants apparaît uniquement après le clic sur ADMIN, plusieurs hypothèses doivent être testées.
Hypothèse A — L'initialisation des assistants dépend d'un état UI
Exemple problématique :
useEffect(() => {
  if (!isAdminOpen) {
    return;
  }

  loadAvailableAgents();
}, [isAdminOpen]);


Dans ce cas, la liste n'est chargée qu'après ouverture de l'interface Admin.
Hypothèse B — La requête IPC n'est pas déclenchée au montage de la page
L'appel :
useSWR('acp.agents.available', fetchAvailableAgents);


peut être conditionné par un enabled, un état de connexion, une route ou un composant qui ne monte qu'après l'action ADMIN.
Hypothèse C — Les assistants sont filtrés
Il est possible que les agents détectés existent bien, mais qu'ils soient filtrés avant d'être affichés :
const visibleAgents = availableAgents?.filter(
  agent => agent.enabled
);


Si le preset n'est pas correctement enregistré, enabled peut être absent, false, ou si le mapping des presets échoue, l'assistant disparaît.
Hypothèse D — Une configuration persistée écrase la valeur par défaut
Votre architecture mentionne :
guid.lastSelectedAgent


Si cette valeur contient encore :
custom:builtin-n8n-workflow


ou une autre sélection, elle peut prendre priorité sur votre useState('n8n').

C'est une piste prioritaire à vérifier avant de modifier à nouveau le code.

9. Solution architecturale alternative — n8n ne devrait pas nécessairement être un ACP backend
Votre intégration n8n est décrite comme un backend HTTP/service, tandis que le système ACP d'origine est organisé autour de la détection et du lancement d'agents CLI.

Il faut donc éviter de confondre :
- ACP backend : moteur de lancement/communication avec les agents ACP ;
- n8n backend : moteur d'exécution de workflows via HTTP ;
- Assistant/preset : choix visible dans l'interface utilisateur ;
- Conversation type : catégorie de conversation persistée et routée dans l'application.
L'ajout de n8n dans AcpBackendAll peut être techniquement valide pour certains types, mais s'il entraîne n8n dans les mécanismes ACP CLI par défaut, ce serait une mauvaise abstraction.
