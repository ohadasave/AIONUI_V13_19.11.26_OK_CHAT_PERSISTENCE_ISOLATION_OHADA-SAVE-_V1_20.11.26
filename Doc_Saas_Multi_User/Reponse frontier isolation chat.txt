5. Modification n°3 — database/index.ts
C'est ici que je supprimerais définitivement le fallback.
Actuellement

À remplacer par
getUserConversations(
  userId: string,
  page = 0,
  pageSize = 50
) {
  if (!userId) {
    console.error(
      '[Database] CRITICAL: userId is required'
    );

    throw new Error(
      'userId is required for getUserConversations'
    );
  }

  console.log(
    `[Database] getUserConversations userId=${userId}`
  );

  const countResult = this.db
    .prepare(
      'SELECT COUNT(*) as count FROM conversations WHERE user_id = ?'
    )
    .get(userId) as { count: number };

  const rows = this.db
    .prepare(`
      SELECT *
      FROM conversations
      WHERE user_id = ?
      ORDER BY updated_at DESC
      LIMIT ? OFFSET ?
    `)
    .all(
      userId,
      pageSize,
      page * pageSize
    );

  return {
    data: rows.map(rowToConversation),
    total: countResult.count,
    page,
    pageSize,
    hasMore:
      (page + 1) * pageSize < countResult.count,
  };
}

1. Ce que les fichiers montrent

La race condition window.__currentUserId est peu crédible au login. Dans login(), l’affectation window.__currentUserId = userId s’exécute de façon synchrone avant setUser(). Les useEffect de React tournent après le commit du rendu suivant, donc la variable est déjà définie. Ce n’est pas elle qui rend undefined.

Le symptôme est cohérent avec cette combinaison :

Un appel de lecture arrive au backend avec userId absent ou égal à system_default_user.

Autrement dit, la DB peut être saine et la fuite venir du fallback, du merge fichier, ou d’un appelant non patché.

Autres défauts qui n’expliquent pas la fuite directement :

Dépendances du useEffect. ChatHistory dépend de [isConversation] et non de l’utilisateur. Si le composant reste monté entre logout et login, la liste d’ALICE reste affichée.
État global conservé. Aucun nettoyage n’est fait au logout : onglets ouverts, caches SWR et état de l’emitter survivent à la déconnexion.
Un seul emplacement de credentials. eaudit_credentials n’en stocke qu’un. Quand BOB se connecte, il écrase ceux d’ALICE, qui ne pourra plus jamais retrouver son userId. Mots de passe en clair dans localStorage.

Sur l’IPC : un { userId: undefined } arrive au backend comme undefined ou comme clé absente. Dans les deux cas, userId || default donne le même résultat. Ce n’est pas une cause distincte.

3. CLAUDE SONNET 


Diagnostic : cause racine probable

Le document formule trois hypothèses, mais le code fourni en désigne une autre, plus structurelle.

1. Cause la plus probable : updateConversation écrase le user_id avec defaultUserId

Dans updateConversation, la ligne conversationToRow(updated, this.defaultUserId) produit un row dont le user_id est defaultUserId. Le UPDATE ne modifie pas user_id (il met à jour name, extra, model, status et updated_at), donc ce point n’est pas une fuite directe. Mais il révèle un schéma : le code passe defaultUserId partout où le contexte utilisateur manque. Il faut vérifier tous les chemins qui appellent createConversation sans userId (import, migration, ConversationService pour les chats « cron », « team » ou « agent », etc.). Un seul chemin de ce type suffit à produire des lignes system_default_user.

2. Cause probable de la fuite visible : les appels IPC qui ne passent pas par getUserConversations

Le fichier ChatHistory ne fait pas que lire. Les appels suivants n’ont pas de userId dans le code fourni :

ipcBridge.conversation.remove.invoke({ id })
deleteConversation(conversationId), qui ne vérifie pas le propriétaire
le getUserConversations du provider, qui retombe sur le file storage sans filtre (hypothèse #3 du document)

Si le provider arrive dans la branche file storage (userId absent ou égal à system_default_user), il fusionne toutes les conversations historiques. C’est le seul chemin du code fourni qui peut montrer « AAAAAA » à Bob sans que la requête SQL soit en cause.

3. La race condition (hypothèse #1) est réelle mais pas la cause principale

Elle est possible mais peu probable dans le cas du login : window.__currentUserId est affecté de façon synchrone avant setUser, donc au rendu suivant il est défini. Le vrai défaut est ailleurs : le useEffect de ChatHistory a pour dépendance [isConversation], pas l’utilisateur.

Scénario de fuite réaliste :

Alice se déconnecte, ChatHistory reste monté (ou est remonté avec le même état).
Bob se connecte, __currentUserId change.
isConversation ne change pas, donc l’effet ne se relance pas.
Le state chatHistory d’Alice reste affiché pour Bob.

getUserConversations(userId: string, page = 0, pageSize = 50): IPaginatedResult<TChatConversation> {

  if (!userId) {
    console.error('[Database] getUserConversations called without userId');
    return { data: [], total: 0, page, pageSize, hasMore: false };
  }

  try {
    const countResult = this.db.prepare(
      'SELECT COUNT(*) as count FROM conversations WHERE user_id = ?'
    ).get(userId) as { count: number };

    const rows = this.db.prepare(`
      SELECT * FROM conversations
      WHERE user_id = ?
      ORDER BY updated_at DESC
      LIMIT ? OFFSET ?
    `).all(userId, pageSize, page * pageSize) as IConversationRow[];

    return {
      data: rows.map(rowToConversation),
      total: countResult.count,
      page, pageSize,
      hasMore: (page + 1) * pageSize < countResult.count,
    };
  } catch (error: any) {
    console.error('[Database] getUserConversations error:', error);
    return { data: [], total: 0, page, pageSize, hasMore: false };
  }
}

5. GEMINI HYDROGEN 

1. Diagnostic clair (Cause racine)
L’isolation échoue en lecture parce que le frontend s’appuie sur un état global impératif (window.__currentUserId) lu dans un useEffect sans dépendance utilisateur ([isConversation]), combiné à un mécanisme de fail-open côté backend (userId || this.defaultUserId + fusion du file storage ProcessChat.get('chat.history')). En React, les useEffect enfants (ChatHistory) s’exécutent avant les useEffect parents (AuthProvider) lors du montage/rechargement, et ne se ré-exécutent pas lors d’un changement de compte si le composant reste monté : ChatHistory envoie userId = undefined (ou l’ID précédent), ce qui déclenche côté backend la requête WHERE user_id = 'system_default_user' et la fusion non isolée du file storage.
Point logique critique que votre doc n’a pas encore vérifié : SQLite ne peut pas retourner la conversation "AAAAA" (créée par A) et "Test BOB" (créée par B) dans une même requête WHERE user_id = ? s’ils avaient deux user_id différents. Donc, si l’utilisateur B voit "AAAAA" dans ChatHistory, cela prouve mathématiquement qu’au moins une des trois conditions suivantes est vraie :
"AAAAA" a en réalité été créée avec user_id = 'system_default_user' (autre point d’entrée de création, ou fallback silencieux dans createConversation / conversationToRow), et la lecture de B retombe aussi sur 'system_default_user'.
"AAAAA" existe dans le file storage (ProcessChat 'chat.history') et la lecture de B passe userId = undefined, activant le merge legacy dans databaseBridge.ts.
Les « données qui se chevauchent » proviennent de composants d’état/UI non réinitialisés au logout (onglets ouverts dans ConversationTabs, cache React ou route /conversation/:id encore active) + d’un bug majeur dans AuthContext.tsx où eaudit_credentials écrase le compte précédent à chaque nouveau login.

Dans les deux cas, le backend reçoit userId === undefined : la cause n’est pas Electron IPC, c’est l’émission d’un userId undefined côté frontend + l’absence de rejet côté backend.
3. Réponses directes à vos 5 questions
Cause la plus probable ? Combinaison Priorité 1 + Priorité 2 (le frontend envoie userId undefined ou stale en lecture, et soit la création de "AAAAA" a aussi fait fallback sur system_default_user, soit le merge ProcessChat l’a remontée). Vérifiable en 30 secondes via le SELECT SQL en Phase 1.
Solution recommandée ? Combinaison complète (Defense in Depth) :
Frontend : useAuth().user?.id partout + annulation des requêtes obsolètes (cancelled) + multi-utilisateurs dans AuthContext + reset complet au logout.
Contrat IPC : userId: string obligatoire dans ipcBridge.ts (pour que tsc détecte 100% des oublis).
Backend/DB : Fail-closed (retourner [] ou lever une erreur si !userId, supprimer defaultUserId en mode multi-utilisateur, désactiver le merge ProcessChat dès qu’un userId non-legacy est utilisé).
Autres points de fuite potentiels ?
ConversationTabs (onglets ouverts persistés globalement dans localStorage).
db.getConversation(id), updateConversation, deleteConversation, getMessages : si B accède à une route /conversation/:id résiduelle de A sans vérification AND user_id = ?, la conversation s’ouvre.
AgentSetupCard / Guid / getCurrentUserId() : tout point d’entrée conversation.create qui lit window.__currentUserId.
Comment garantir l’isolation à 100% ? Typage strict (userId: string), suppression de tout fallback silencieux, scoping SQL WHERE id = ? AND user_id = ? sur lecture/écriture/suppression, et tests automatisés Vitest sur database/index.ts.
Mode WebUI : Attention ! En WebUI (single/admin auth), le user seeded en base a souvent id = 'system_default_user' (ou l’ID retourné par /api/auth/me). Il ne faut donc pas rejeter 'system_default_user' si AuthContext WebUI retourne cet ID explicitement — en revanche, il faut toujours rejeter undefined ou "", et ne jamais fusionner ProcessChat pour les comptes user_*.

getUserConversations(userId: string, page = 0, pageSize = 50): IPaginatedResult<TChatConversation> {
  if (!userId || typeof userId !== 'string' || !userId.trim()) {
    console.error('[Database] CRITICAL: getUserConversations called without userId');
    throw new Error('userId is required for getUserConversations');
  }

  const countRow = this.db
    .prepare('SELECT COUNT(*) as count FROM conversations WHERE user_id = ?')
    .get(userId) as { count: number };

  const rows = this.db
    .prepare(`
      SELECT * FROM conversations
      WHERE user_id = ?
      ORDER BY updated_at DESC
      LIMIT ? OFFSET ?
    `)
    .all(userId, pageSize, page * pageSize);

  return {
    data: rows.map(rowToConversation),
    total: countRow.count,
    page,
    pageSize,
    hasMore: (page + 1) * pageSize < countRow.count,
  };
}

// Helpers dans src/renderer/context/AuthContext.tsx
interface DesktopUserRecord {
  username: string;
  password: string;
  userId: string;
}

const DESKTOP_USERS_KEY = 'eaudit_desktop_users';
const LEGACY_CREDENTIALS_KEY = 'eaudit_credentials';

function loadDesktopUsers(): Record<string, DesktopUserRecord> {
  const users: Record<string, DesktopUserRecord> = {};
  try {
    const raw = localStorage.getItem(DESKTOP_USERS_KEY);
    if (raw) {
      Object.assign(users, JSON.parse(raw));
    }
    // Migration douce depuis l'ancien format mono-utilisateur
    const legacyRaw = localStorage.getItem(LEGACY_CREDENTIALS_KEY);
    if (legacyRaw) {
      const legacy = JSON.parse(legacyRaw) as Partial<DesktopUserRecord>;
      if (legacy.username && legacy.password && legacy.userId) {
        const key = legacy.username.trim().toLowerCase();
        if (!users[key]) {
          users[key] = {
            username: legacy.username,
            password: legacy.password,
            userId: legacy.userId,
          };
          localStorage.setItem(DESKTOP_USERS_KEY, JSON.stringify(users));
        }
      }
    }
  } catch (e) {
    console.error('[AuthContext] Failed to parse desktop users:', e);
  }
  return users;
}
